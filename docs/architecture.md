# 架构详解

> 本文档详细解释钱喵 AI 财务助手的三层分离架构和引擎处理流水线。

## 三层分离架构

### 设计理念

传统 AI 助手把"引擎逻辑"和"业务知识"混在一起，导致换行业就要重写整个系统。钱喵的核心设计决策是：**引擎不知道任何业务知识，所有行业规则都放在用户拥有的经验包中**。

这意味着同一个引擎，加载水务经验包就能做水务财务分析，加载制造业经验包就能做制造业财务分析——引擎代码一行都不用改。

### 层级职责

**引擎层（core/）**

7 个文件定义全部行为：系统指令、经验包加载、规则扫描、Gate 校验、引用语法、独立审查。引擎层不包含任何行业规则、报告模板或业务数据。

特性：
- 不可变（仅版本升级时变更）
- 领域无关（不内置任何行业知识）
- 平台无关（纯 Markdown，任何 AI 平台可用）

**配置层（packs/）**

经验包是配置层的核心单元，承载所有行业知识。每个经验包包含四层（L1-L4），用户可自由增删改。

特性：
- 用户拥有（完全可控）
- 可替换、可升级、可 DIY
- 纯约定扫描（无 pack.yml，目录结构即元数据）

**数据层（data-buffer/）**

用户脱敏数据的入口和 AI 产出的出口。全部 `.gitignore`，不进入版本控制。

特性：
- 即用即弃（每次任务不同）
- 数据责任归用户（脱敏由用户负责）
- 模板可提交（`templates/` 目录）

## 引擎处理流水线

### 七阶段流程

```
数据接入 → Gate-1 数据准入 → 规则预扫描 → AI 处理 → 审计执行 → Gate-2 产出校验 → 产出 + L4 记录
```

### 阶段一：数据接入

用户通过 `data-buffer/input/` 提供已脱敏的数据，或直接在对话中粘贴。数据层全部 `.gitignore`。

### 阶段二：Gate-1 数据准入

三项检查，均非阻断：
1. **数据格式确认**：自动检测 CSV/Excel/文本/JSON，格式不符时提示转换
2. **脱敏提示**：一次性提示"请确认数据已脱敏"
3. **技能选择**：根据数据特征确定使用哪些 L2 模板和 L1 规则，输出加载清单

加载清单格式：`core(全部) + context(命中的文件列表)`

### 阶段三：规则预扫描

加载当前经验包的 L1 规则（core 全部 + context 按关键词命中的文件）和 L4 决策记录。

L1 两层加载机制：
- **core 规则**：始终全量加载，<=10 条，领域无关
- **context 规则**：解析文件头 `keywords` 字段，用户输入命中关键词时加载该文件

### 阶段四：AI 处理

按 L2 模板编排执行任务：
- 严格按模板的任务流程和产出格式组织内容
- 引用的 L1 规则作为硬约束
- 参考 L3 案例的方法论（非强制）

### 阶段五：审计执行

按 L1 规则对产出执行审计扫描，生成提示清单。详见规则扫描器部分。

### 阶段六：Gate-2 产出校验

两个独立环节，顺序执行但互不阻断：

**第一环节 - 规则扫描（RULE_SCANNER）**：
- L1 规则符合性（逐条 YAML 匹配）
- L2 模板骨架符合性（`##` 章节检查）
- L3 案例一致性（方法论方向对比）
- Instinct 召回（domain + trigger 匹配，confidence 分流）

**第二环节 - 独立审查（REVIEWER）**：
- 预报告门控四问（全"是"才报告）
- 误报清单过滤（6 类主观建议跳过）
- 五维度审查（L1/L2/L3/勾稽/敏感信息）

### 阶段七：产出与 L4 记录

Gate-2 通过后：
- 产出写入 `data-buffer/output/`
- AI 自动在 `L4-decision-logs/` 创建决策记录（含证据链）

## 模式识别

| 模式 | 触发词 | 行为 |
|------|--------|------|
| 完整模式 | "分析""报告""审计" | 七阶段完整执行 |
| 轻量模式 | "看看""检查一下" | 跳过 L2 编排，直接分析，Gate-2 仍执行 |
| 紧急模式 | "紧急""马上" | 最精简执行，Gate-1 仅做脱敏提示 |

## 规则扫描器（RULE_SCANNER）

### core vs context 规则区分

| 维度 | core 规则 | context 规则 |
|------|----------|-------------|
| 加载来源 | `L1-rules/core/*.yml` | `L1-rules/context/*.yml`（仅命中的文件） |
| 加载时机 | 始终加载 | 关键词命中时加载 |
| 来源标注 | `core/{file}.yml#{rule-id}` | `context/{file}.yml#{rule-id}（按需加载）` |

### 规则类型

5 种规则类型：数值比较型、文本匹配型、勾稽校验型、模板引用型、自定义逻辑型。

### Instinct 召回

规则扫描完成后，扫描 `instincts/` 目录下所有 YAML，按 domain + trigger 匹配：
- confidence >= 0.7：自动应用，action 嵌入产出
- confidence 0.3-0.6：仅提示
- confidence < 0.3：静默跳过

### evidence_chain 证据链

L4 决策记录的 `## 证据链` 章节记录全链路证据追踪，包含 6 个子节。规则扫描时加载 evidence_chain 用于历史参考。

## 引用语法

8 种引用格式连接四层经验包和审查 agent：

```
[L1:core:name]      → 核心规则
[L1:context:name]   → 上下文规则
[L1:name]           → 默认（先 core 再 context）
[L2:name]           → 模板
[L3:name]           → 案例
[L4:name]           → 决策记录
[L4:instinct:name]  → 直觉经验卡片
[REVIEWER]          → 独立审查 agent
```

L2 模板在头部 `rules:` 声明中引用 L1 规则，Gate-2 阶段优先校验这些规则。

## 独立审查 agent（REVIEWER）

### 设计目的

规则扫描器按 YAML 规则机械匹配，能检测数值越界和文本模式，但无法做专业判断。REVIEWER 以财务专业视角做二次审查，两者互补。

### 预报告门控

报告任何问题前必须通过四问：
1. 能否指出产出中确切的位置？
2. 能否描述具体的错误模式？
3. 是否对照了 L1 规则原文？
4. 严重性是否合理？

四问任一为"否"，该发现不报告。

### 误报清单

6 类必须跳过的"发现"：建议增加分析维度、建议补充说明、建议参考案例、数字看起来偏高/偏低、建议添加风险提示、格式可以更美观。

## 多包叠加

多个经验包可同时加载，叠加规则：
- L1 core：后加载覆盖先加载（同名 id）
- L1 context：各包独立维护关键词
- L2 模板：后加载覆盖先加载（同名文件）
- L3 案例：合并，不覆盖
- L4 决策记录：各包独立

## 向后兼容

- 无 `core/context` 子目录的旧格式 L1 规则自动全量加载
- `[L1:name]` 默认语法有 core/context 时先查 core 再查 context，无子目录时直接查 `L1-rules/`
- 最低经验包版本 `>=1.0.0`
